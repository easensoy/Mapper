# Mapper → HMI data contract: what should be passed, what is missing

**Date:** 2026-07-26
**Trigger:** `Jyotsna\BarCodeReaderFB.pptx` (9 slides). Barcode reading and recipe *selection* are
deliberately out of scope here — this document extracts only what the deck implies about the
**data the Mapper must hand to the HMI**, then measures the current Mapper against it.

**Status of this document:** investigation only. No Mapper code, CAT, Control.xml, syslay or
sysres was modified. Every claim below is labelled **VERIFIED** (read from a deployed artefact
in `C:\Demonstrator` or from the reference solution), **INFERENCE**, or **UNKNOWN**.

---

## 1. What the deck actually asks for

Ignoring the barcode reader and the `BarCodeRecipeHeaderTable`, three things in the deck are
statements about the **Mapper's output**:

**Slide 2 — "Data Generated by Mapper".** The `RecipeStepTable` with columns
`Index / StepType / CmdTargetName / CmdStateArr / NextStep`.

**Slide 5 — three operating modes.**

| Mode | Name | HMI role |
|---|---|---|
| 1 | Automatic | recipe runs itself; manual buttons disabled; Start / Stop / Reset / Pause |
| 2 | Manual | operator walks the recipe step by step from the HMI |
| 3 | Setup | operator drives individual actuators directly |

**Slide 9 — the richer step table the HMI needs**, plus manual-mode command inputs on the
process FB (`HMI_ExecuteStep`, `HMI_NextStep`, `HMI_PreviousStep`, `HMI_ResetStep`):

| StepID | StationID | ActuatorID | TargetState | StepText | AutoNextAllowed |
|---|---|---|---|---|---|
| 1 | Feed | FeederCylinder | Work | Move feeder cylinder to Work | TRUE |
| 2 | Feed | FeederCylinder | Home | Return feeder cylinder Home | TRUE |
| 3 | Assembly | Gripper | Close | Close gripper | TRUE |
| 4 | Assembly | PnP | Work2 | Move pick-and-place to Work2 | TRUE |

That table is the crux. It is **not** a control structure — the controller does not need
`StationID`, `ActuatorID`, `TargetState` or `StepText` to execute anything. It is a **presentation
contract**: the strings the operator reads. Slide 7 makes the same point for Setup mode, where
the HMI is expected to label buttons per actuator ("Feed Cylinder [Move Home] [Move Work]",
"Rotary Actuator [Home] [Work1] [Work2]").

**So the deck's demand, reduced to one sentence: the Mapper must pass human-readable identity
and intent — component names, station names, target-state names, step descriptions — alongside
the numeric control data it already emits.**

## 3. The naming gap — root cause found

This is the "PATH-macro-like thing" in the question. There **is** a dedicated channel for it, it
**is** already wired, and it is **dead because one event connection is missing**.

### 3.1 The channel exists

**VERIFIED** — `Five_State_Actuator_CAT_HMI.fbt` (the HMI service-interface FB) declares:

```xml
<Event ID="23DDB2ACA3C5EEE" Name="name_event">
  <With Var="component_name" />
  <With Var="ModeCMD" />
</Event>
...
<VarDeclaration ID="1FFB7060598B96F8" Name="component_name" Type="STRING" />
```

**VERIFIED** — the faceplate consumes it. `Five_State_Actuator_CAT_sDefault.cnv.xml`:

```xml
<Event Name="name_event">component_name;ModeCMD</Event>
<Input Name="component_name" Type="STRING" />
```

and `…sDefault.cnv.Designer.cs` places **three** controls bound to it — a `FreeText` at the tile's
top-left corner (`DesignMatrix … 8D, 8D`), a stretched `FreeText` header bar, and a `Label`
background — all with `TagName = "component_name"`. **The tile is designed around a name header.**

### 3.2 The channel is wired inside the CAT

**VERIFIED** — `Five_State_Actuator_CAT.fbt`:

```xml
<Connection Source="actuator_name" Destination="FB13.IN1" />        <!-- data in  -->
<Connection Source="FB13.OUT1"     Destination="IThis.component_name" />  <!-- data out -->
<Connection Source="FB13.CNF"      Destination="IThis.name_event" />      <!-- publish  -->
```

`FB13` is `ANY2ANY_85FE4D6C8D3ACAD8`.

### 3.3 …but it is never triggered

**VERIFIED** — the `ANY2ANY` library type
(`Runtime.Base-24.1.0.22\Files\Runtime.Standard\ANY2ANY.fbt`) has exactly one event input:

```xml
<EventInputs><Event Name="REQ"><With Var="IN${CNT}" /></Event></EventInputs>
<EventOutputs><Event Name="CNF"><With Var="OUT${CNT}" /></Event></EventOutputs>
```

It is strictly event-driven: `OUT1` is computed and `CNF` fires **only** on `REQ`.

**VERIFIED** — the complete set of connections whose destination is `FB13.*` in
`Five_State_Actuator_CAT.fbt` is:

```
<Connection Source="actuator_name" Destination="FB13.IN1" />
```

**There is no `→ FB13.REQ`.** Therefore `FB13.CNF` never fires, `name_event` never fires, and
`component_name` is never delivered. **Every actuator faceplate renders with a blank name
header.** Identical in `Seven_State_Actuator_Centre_Home_CAT.fbt`, and identical in Jyotsna's
reference `Five_State_Actuator_CAT.fbt` — so this is a long-standing omission, not something the
Mapper introduced.

### 3.4 The proof that it is an omission, not a design choice

**VERIFIED** — the same author's `Area.fbt` uses the *same* ANY2ANY idiom and gets it right:

```xml
<Connection Source="INIT"     Destination="Name.REQ" />          <!-- ← the trigger -->
<Connection Source="AreaName" Destination="Name.IN1" />
<Connection Source="Name.CNF" Destination="AreaHMIAdptrIN.ANREQ" />
<Connection Source="Name.OUT1" Destination="AreaHMIAdptrIN.AreaName" />
```

The actuator CATs have three of those four lines. The missing one is `INIT → FB13.REQ`.
`Five_State_Actuator_CAT` already has a boundary `INIT` event that fans out to
`StateHandling.INIT` and `Poll.START`, so the connection is a pure addition with no restructuring.

## 4. Per-CAT name-channel status

**VERIFIED**, traced connection by connection in the deployed CATs:

| CAT | HMI name port | Data source | Trigger | Live? |
|---|---|---|---|---|
| Five_State_Actuator_CAT | `component_name` | `actuator_name → FB13` | **`FB13.REQ` unwired** | ❌ dead |
| Seven_State_Actuator_Centre_Home_CAT | `component_name` | `actuator_name → FB13` | **`FB13.REQ` unwired** | ❌ dead |
| Sensor_Bool_CAT | `name` declared on the SIFB | **nothing connects `IThis.name`** | — | ❌ dead |
| Station_CAT | `StationName`, `ParentName` | `Station.StationName` InputVar → HMI adapter | `Status.INITO → SREQ` ✅ | ⚠️ **wired, but the Mapper sets no value** |
| Area_CAT | `Area_Name` | `Area.AreaName` InputVar → `Name` ANY2ANY | `INIT → Name.REQ` ✅ | ⚠️ **wired, but the Mapper sets no value** |
| Process1_Generic | `ActuatorName` (on `stateUpdate`) | `ANString.OUT1`; **`ANString.IN1` unconnected** | `stateUpdate` has **no driver** | ❌ dead |
| Robot_Task_CAT | *none* | — | — | ❌ no port exists |

Four distinct failure modes, and they need four different answers:

* **A. Wired and triggered, value not supplied** — Station, Area. *Mapper-only fix.*
* **B. Wired, never triggered** — Five_State, Seven_State. *One CAT connection each.*
* **C. Port declared, never connected** — Sensor_Bool. *CAT wiring + a trigger.*
* **D. No port at all** — Robot_Task. *CAT interface change.*

## 5. `actuator_name` is the wrong string to display

Even once triggered, `component_name` would render **`bearing_pnp`**, not `Bearing PnP`.

**VERIFIED** — `actuator_name` is the **ring protocol key**. `updateComponentState`'s `BREQ`
algorithm does `IF component_state_in.dest_name = name THEN state_cmd := …`, a **case-sensitive**
ST string compare, and `TemplateMap.RingKey` lower-cases it precisely so both producers agree.
The same string is also the MQTT topic (`actuator_name → MqttPub.Topic1`).

So `actuator_name` is load-bearing for the ring and for MQTT and **must stay lower-case**. A
display name is a *different* value and needs its own parameter. (Sensors are already fine —
`Sensor_Bool_CAT` is parameterised with the verbatim `name`, e.g. `'PartInHopper'`.)

This is the single most important design conclusion in this document: **the HMI needs a display
name that is not the ring key.**

## 6. Step text: what the HMI can show today

**VERIFIED** — `Process1_Generic` *does* have a live step-text path:

```
ProcessEngine.SCNF → TSString.REQ / NSString.REQ / PSString.REQ
ProcessEngine.ThisStepText → TSString.IN1   (and Next/Previous equivalents)
TSString.OUT1 → IThis.ThisStepText          TSString.CNF → IThis.SCNF
```

**But** `ProcessRuntime_Generic_v1.fbt` computes those strings as **engine-phase literals**:

```
ThisStepText := 'Initialised' | 'Command step' | 'Wait step' | 'End step'
              | 'Sending command' | 'Advancing to command' | 'Waiting for target state'
```

They describe what the *engine* is doing, not what the *machine* is doing. Slide 9 wants
"Move feeder cylinder to Work". `RecipeStep` has no text field, so the model-derived description
does not exist anywhere in the generated system.

**Also broken:** `ANString.REQ` is driven by `ProcessEngine.SCNF`, but **`ANString.IN1` has no
data source** (it should be `ProcessEngine.cmd_target_name`, which the engine does output), and
`IThis.stateUpdate` — the event that carries `ActuatorName` + `StateValue` — has **no driver at
all**. So the process faceplate cannot even name the actuator it is currently commanding.

## 7. Manual mode (Mode 2) — contract comparison

**VERIFIED** — diff of `Process1_Generic_HMI.fbt`, ours vs the reference. The reference declares
13 ports we do not:

```
ManualExecuteStep   ManualNextStep   ManualStepReady   ManualStepComplete
OperatorInstruction ProcessName      ProcessComplete
CurrentStep         CurrentStepType  WaitSatisfied     ModeCMD
MREQO               NSREQO
```

Mapped onto slide 9: `ManualExecuteStep`/`ManualNextStep` are the deck's `HMI_ExecuteStep`/
`HMI_NextStep`; `OperatorInstruction` is `StepText`; `ProcessName` is `StationID`;
`ManualStepReady`/`ManualStepComplete` are the handshake behind `AutoNextAllowed`.

**Jyotsna has already designed the HMI-side contract for manual mode. Our process FB does not
implement it, and our engine has no manual-hold state.** This is the largest single gap, and the
only one that requires changing the runtime engine's ECC — i.e. genuine control-logic work, not
presentation work.

## 8. Setup mode (Mode 3) — already works

Worth stating plainly, because it is the deck's slide 7 and it is **not** a gap.

**VERIFIED** — the HMI→PLC jog path is complete in both actuator CATs:

```
IThis.cmd_event → ActuatorCore.setup_event
IThis.toWork    → ActuatorCore.toWorkSetup
IThis.toHome    → ActuatorCore.toHomeSetup
              (+ toWork1Setup / toWork2Setup on the seven-state swivel)
```

`ModeCMD` reaches every actuator via `stationAdptr_in.ModeCMD → IThis.ModeCMD`, and the core's
launch arcs already carry the `mode = 3 AND toWorkSetup` disjunct. The `sSetup` faceplate exists
in the template library for both actuator families, and the HMI generator already emits a
`SetupScreen` family from it.

**Setup mode should be operable today once a Station is put in mode 3.** It has never been
exercised on the rig — that is the recommended first demonstration, since it needs no new code.

⚠️ Mode 3 drives actuators directly, bypassing the recipe. Interlocks still apply
(`InterlockManager` gates the core arcs), but this is operational interlocking, **not a safety
function**. Do not exercise Setup mode on the bench rig while the clamp damage and swivel
collision risk documented in `CLAUDE.md` are outstanding.

## 10. Recommended order

**Step 1 — Station and Area names (Mapper-only, zero CAT change).**
`Station.fbt` declares `StationName : STRING`, wires it to `StationHMIAdptrIN.StationName`, and
publishes it on `Status.INITO → SREQ`. `Area.fbt` does the same via its `Name` ANY2ANY, correctly
triggered from `INIT`. **Both are complete and waiting for a value the Mapper never writes.**
Adding `StationName` / `AreaName` parameters in `SystemLayoutInjector` is display-only and
touches no control path. This is the cheapest real improvement available.
⚠️ Note `Station.StationName` also feeds `StationAdaptrOUT.ParentName`, which propagates down as
a child's `ParentName` — also display-only, but worth confirming on screen.

**Step 2 — trigger the actuator name (2 lines).**
Add `<Connection Source="INIT" Destination="FB13.REQ" />` to `Five_State_Actuator_CAT.fbt` and
`Seven_State_Actuator_Centre_Home_CAT.fbt`, exactly mirroring `Area.fbt`. Tiles then show
`feeder`, `bearing_pnp`, … — lower-case, but no longer blank.

**Step 3 — a real display name.**
Add a `display_name : STRING` InputVar to the two actuator CATs, route it to `FB13.IN1` in place
of `actuator_name`, and have the Mapper write the verbatim Control.xml component name
(`'Bearing PnP'`). `actuator_name` keeps its ring/MQTT duty untouched. Do **not** try to reuse
`actuator_name` for display — see §5.

**Step 4 — process tile.** Connect `ProcessEngine.cmd_target_name → ANString.IN1` and drive
`IThis.stateUpdate` from `ProcessEngine.SCNF`.

**Step 5 — sensor and robot names.** Wire `IThis.name` in `Sensor_Bool_CAT` (value already
present); add a name port to `Robot_Task_CAT`.

**Step 6 — the step table (slide 9).** Extend `RecipeStep` with `StationID`, `ActuatorID`,
`TargetState`, `StepText`, `AutoNextAllowed`; have `ProcessCompiler` fill them from Control.xml
(it already knows the process, the target component and the destination state name, so the text
is derivable without new model data); have the engine publish `Recipe[CurrentStep].StepText`
instead of its phase literals. This is where the deck's real value is: it turns a numeric recipe
into an operator-readable one.

**Step 7 — manual mode.** Only after 1–6. It needs the 13 SIFB ports *and* a hold state in the
engine ECC so `AdvanceStep` waits for `ManualExecuteStep` when `Mode = 2`. This is control-logic
work on the rig-proven engine and should be gated behind its own byte-identical verification.

**Steps 2–7 all modify CAT internals or the process engine, which the current standing scope
explicitly protects. None of them should proceed without an explicit instruction.** Step 1 does
not touch a CAT, but it does change the generated syslay/sysres, so it breaks byte-identity by
design and needs the usual regeneration proof.

## 11. Not investigated / unknown

* Whether the reference HMI displays names by some path other than `component_name` — **UNKNOWN**;
  the ANY2ANY is provably untriggered in her CAT too, so if her tiles show names, the mechanism is
  elsewhere and has not been found.
* Whether `Station.StationName` reaches the faceplate at runtime once populated — **INFERENCE**
  from the wiring; not observed on the panel.
* Barcode reading, `BarCodeRecipeSelector`, `BarCodeRecipeHeaderTable`, multi-recipe
  `StartIndex`/`StepCount` windowing — **deliberately excluded** per instruction. Note that if
  multi-part recipes are ever adopted, `RecipeStep` becomes a shared pool and the engine needs
  the start/count window; that is a separate design.
