# Bearing_PnP Neutral Startup

## Status

SUPERSEDED on 2026-07-25 after a rig run.

The output-neutral startup described below (report the sensed position while
writing both coils FALSE) was generated and tested physically. Bearing_PnP still
moved during first-cycle initialization: both coils FALSE leaves a
three-position pneumatic unheld, and nothing ever commands it home, so the arm
drifts and the first recipe command starts from an unknown position.

The durable fix is now the rig-proven Ground Truth startup: a startup work
sensor reading routes `INIT -> ToHome`, driving the arm to its centre reference
and holding it there. It is generated by the single writer
`SwivelCatPatcher.PatchSwivelStartupToHome`, and the generated
`SevenStateCentreHomeActuator.fbt` is byte-identical (SHA256) to the reference
project's. See invariant I-16.

The analysis below is retained because the symptom description and the
first-cycle-only reasoning remain accurate; only the chosen remedy changed.

## High-Level Explanation

Bearing_PnP moved during the first cycle even though the recipe had not
commanded it. Later cycles behaved correctly.

The movement was not caused by the process recipe or the M580 resource wiring.
The swivel's internal ECC interpreted its startup sensor reading by entering a
normal operating state. Those normal states also write physical outputs, so
recognising the initial position accidentally became a movement command.

The fix separates two responsibilities:

1. Observe and report where the swivel is at startup.
2. Energise a coil only after an explicit operating command.

At startup, the CAT now reports Home, Work1, or Work2 as appropriate while
forcing both work outputs FALSE. Normal recipe commands still use the existing
movement states after initialization.

## Observed Symptom

- The problem occurred only after application initialization or a fresh deploy.
- Bearing_PnP moved while Feed was still executing.
- Removing the bearing did not prevent the startup movement.
- The second and later process cycles behaved normally.
- The working Ground Truth project did not visibly reproduce the movement.

The first-cycle-only pattern was the important clue: `INIT` executes once,
whereas recipe command processing executes every cycle.

## Evidence

The investigation established:

1. The current M580 `.sysres` was byte-identical to the working Ground Truth
   M580 `.sysres`.
2. The relevant process recipes were therefore not the behavioral difference.
3. The generated `SevenStateCentreHomeActuator.fbt` contained startup
   transitions into output-writing operating states.
4. `AtWork1` writes `outputToWork1 := TRUE`.
5. `ToWork2` writes `outputToWork2 := TRUE`.
6. Entering either state from `INIT` could energise a valve before any recipe
   command was issued.

The Ground Truth variant used startup recovery through `ToHome`. That happened
to behave correctly with its tested initial position, but `ToHome` also writes
a physical coil. It was not a general no-motion startup guarantee.

## Root Cause

The CAT conflated position classification with actuator control.

The problematic startup behavior was equivalent to:

```text
INIT + Work1 sensor -> normal Work1 state -> Work1 coil TRUE
INIT + Work2 sensor -> normal Work2 movement state -> Work2 coil TRUE
```

This explains why:

- recipe and interlock edits did not solve it;
- the symptom was independent of bearing presence;
- the symptom appeared only on the first cycle;
- copying the Ground Truth recipe and sysres was insufficient.

An identical recipe does not guarantee identical startup behavior when the
fixed CAT logic, physical sensor state, compiled EAE image, or initialization
path differs.

## Generated ECC Behavior

`PatchSwivelNeutralStartup` adds two startup-only ECC states:

- `StartupAtWork1`
- `StartupAtWork2`

Their algorithms are:

```iecst
current_state_to_process := 2;
outputToWork1 := FALSE;
outputToWork2 := FALSE;
```

and:

```iecst
current_state_to_process := 4;
outputToWork1 := FALSE;
outputToWork2 := FALSE;
```

The startup classification is now:

| Startup inputs | Destination | Reported state | Work1 output | Work2 output |
| --- | --- | ---: | --- | --- |
| No work sensor active | `AtHomeInit` | Home | FALSE | FALSE |
| Work1 active only | `StartupAtWork1` | 2 | FALSE | FALSE |
| Work2 active only | `StartupAtWork2` | 4 | FALSE | FALSE |

The startup states publish both `pst_out` and `output_event`. Reporting the
state updates the control system, while `output_event` ensures the physical
output writer receives the FALSE/FALSE values.

The normal outgoing transitions are preserved:

- `StartupAtWork1` can later accept the existing Work2 and Home commands.
- `StartupAtWork2` can later accept the existing Work1 and Home commands.
- A later sensor update with both work sensors FALSE reclassifies to
  `AtHomeInit`.
- `RESET` returns either startup state to `INIT`.

No polling, delay, custom FB, recipe row, or new control channel is introduced.

## Deployment Procedure

1. Close EAE fully before generation.
2. Generate IEC 61499 code from VueOne.
3. Confirm the generated swivel core contains `StartupAtWork1` and
   `StartupAtWork2`.
4. Reopen EAE.
5. Build the generated project.
6. Deploy M580, or deploy all controllers when the overall project changed.
7. Confirm both Bearing_PnP work outputs are FALSE before the first explicit
   recipe command.

Reloading an already-open EAE project can retain or rewrite an older in-memory
model. A fresh reopen is required when validating generated FB type changes.

## Regression Checks

A generated swivel core is correct only if:

- `INIT` does not enter `AtWork1`, `AtWork2`, `ToWork1`, `ToWork2`, or
  `ToHome` because a work sensor is active;
- work-sensor startup paths enter the neutral startup states;
- both startup algorithms assign both outputs FALSE;
- both startup states publish `output_event`;
- normal post-startup recipe transitions remain present;
- the generated project passes syslay/sysres and HCF validation.

## Do Not Reintroduce

Do not solve this symptom by:

- changing the Bearing_PnP recipe;
- adding an AtWork2 staging move;
- changing bearing sensor polarity;
- adding a poll or delay;
- directing `INIT` to a normal work state;
- directing `INIT` to `ToHome`;
- relying on a particular physical startup position;
- copying only the Ground Truth sysres.

Those approaches either address the wrong layer or can still energise a coil
during initialization.
